# 整合人操作手册

> 整合人是协作的守门员，负责 PR 评审、合并主干、统一风格、协调冲突。
> 这个角色可以是人，也可以是一个专门的 agent。

---

## 整合人的职责

1. **PR 评审**：把关质量、风格、接口一致性
2. **合并主干**：把通过评审的 PR 合并进 main
3. **冲突调解**：多 agent 改到一块儿时，协调谁改、怎么合
4. **风格统一**：发现风格漂移时及时纠正
5. **任务拆解**：把大任务拆成可并行的小模块，定义好接口
6. **看板维护**：确保 STATUS.md 状态准确

---

## PR 评审清单

每个 PR 过一遍以下检查项：

### 功能正确性
- [ ] 做的事情和任务描述一致吗？
- [ ] 边界情况处理了吗？（空值、异常、极端输入）
- [ ] 有没有引入明显的 bug？

### 接口一致性
- [ ] 模块之间的接口符合约定吗？
- [ ] 接口有变更的话，有没有同步通知依赖方？
- [ ] 数据格式统一吗？（时间、金额、ID 类型等）

### 代码质量
- [ ] 命名清晰吗？
- [ ] 复杂逻辑有注释吗？
- [ ] 有没有重复代码可以抽？
- [ ] 错误处理到位吗？

### 风格统一
- [ ] 符合 `style-guide.md` 吗？
- [ ] 和项目已有代码风格一致吗？
- [ ] 术语用的是术语表里的吗？

### 协作规范
- [ ] 只改了该改的文件吗？（没有顺手改别人的模块）
- [ ] 提交信息规范吗？
- [ ] STATUS.md 更新了吗？
- [ ] 文档同步更新了吗？

## 评审意见怎么写

### 好的评审意见
- 具体指出问题在哪、为什么是问题、建议怎么改
- 分轻重缓急：「必须改」和「建议改」分开
- 肯定做得好的地方

例子：
```
## 必须改
1. `login.js` 第 42 行，密码错误时没有限制重试次数，有暴力破解风险
   → 建议加个 5 次锁定，参考 `docs/style-guide.md` 错误处理部分

## 建议改
1. 变量名 `usr` 可以改成 `user`，更清晰
2. 可以把验证逻辑抽成单独的函数，方便复用
```

### 不好的评审意见
- 「这里写得不好」——哪里不好？怎么算好？
- 「重新写」——太笼统，给具体方向
- 大量风格问题但之前没给规范——先统一规范再要求

## 合并操作流程

```bash
# 1. 确保本地 main 是最新的
git checkout main
git pull origin main

# 2. 本地预览 PR 分支（可选，但推荐）
git fetch origin
git checkout agent/alice/login-page
# 跑测试、看效果

# 3. 回到 main，合并
git checkout main
git merge --no-ff agent/alice/login-page
# 用 --no-ff 保留合并节点，方便回溯

# 4. 推送
git push origin main

# 5. 删除远端工作分支
git push origin --delete agent/alice/login-page
```

> 用平台的 Merge 按钮也可以，选择「Create a merge commit」（不要 squash，也不要 rebase merge），保留完整历史。

## 冲突处理

### 预防为主
- 拆任务时尽量让不同 agent 碰不同的文件
- 接口先定好，减少返工

### 真冲突了怎么办
1. 谁后提交谁先尝试解决（因为他改的时候应该知道前面有人改了）
2. 解决不了，找整合人
3. 整合人的处理原则：
   - 功能优先：哪边逻辑更重要就保留哪边
   - 都重要的话，讨论怎么合并逻辑
   - 实在谈不拢，谁先提交的优先，后提交的改自己的去适配

## 风格不统一怎么办

### 评审阶段发现
- 小问题：在 PR 评论里指出来，让作者改
- 大问题/系统性问题：
  1. 先合并功能（别卡着）
  2. 单独开一个 style 类型的任务，统一整理
  3. 更新 `style-guide.md`，避免下次再出同样的问题

### 已经合并到 main 了才发现
- 单独开 PR 修，不要在功能 PR 里混着风格修改
- 风格整理 PR 只改格式，不动逻辑，方便 review

## 任务拆解原则

好的任务拆解 = 并行效率高 + 合并冲突少 + 整合成本低

### 按什么拆
**按功能模块拆**，不按技术层拆。

✅ 好的拆法：
- A 做登录页（页面 + 样式 + 表单逻辑）
- B 做用户 API（路由 + 数据库 + 缓存）
- C 做权限中间件

❌ 不好的拆法：
- A 写 HTML
- B 写 CSS
- C 写 JS
（三个人都改同一个文件，天天冲突）

### 拆完要给什么
每个任务交付时必须明确：
1. 做什么（功能范围）
2. 不做什么（边界）
3. 输入是什么（从哪来、格式）
4. 输出是什么（给谁、格式）
5. 依赖谁（等谁的产出）
6. 谁依赖我（我的产出给谁用）

## 每日节奏建议

1. **早上**：看一遍所有待评审的 PR，处理掉
2. **中午**：扫一眼 STATUS.md，有没有人卡着、有没有冲突风险
3. **下午**：处理风险和阻塞，协调资源
4. **下班前**：确认当天该合并的都合了，看板状态准确

不用时时刻刻盯着——看板机制就是为了让大家自主推进，整合人只在卡点时介入。
